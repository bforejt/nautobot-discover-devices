# Interface field mapping

This reference targets the installed Nautobot **3.2.5** model. Discovery uses RESTCONF JSON and records the source of each fact. Existing populated inventory is preserved; an observed disagreement is reported. The baseline handles identity, interface attributes, LAG membership, and reviewed Module ownership. Current enrichment covers 802.1Q mode, scoped VLAN assignments and the complete observed VLAN catalog, operational speed, configured duplex, and explicitly reported RJ45 connectors. Partial switchport configuration remains available in the discovery report when a native field cannot represent it accurately.

The [versioned Interface documentation](https://raw.githubusercontent.com/nautobot/nautobot/v3.2.5/nautobot/docs/user-guide/core-data-model/dcim/interface.md), [model](https://github.com/nautobot/nautobot/blob/v3.2.5/nautobot/dcim/models/device_components.py), [choices](https://github.com/nautobot/nautobot/blob/v3.2.5/nautobot/dcim/choices.py), and [forms](https://github.com/nautobot/nautobot/blob/v3.2.5/nautobot/dcim/forms.py) define the intended semantics and constraints. When prose is stale, the installed model and validators determine valid writes. For example, the documentation still describes exclusive Device/Module ownership, while 3.2.5 stores the root Device on Module-owned components too; both fields are valid when their roots agree.

The following table covers every forward native Interface field, including inherited bookkeeping fields. “Future” means the field has an appropriate native home but requires additional structured evidence and identity rules before this job writes it.

| Field | Meaning and mapping contract | Discovery scope |
| --- | --- | --- |
| `id` | Stable Nautobot UUID. Reuse the existing interface after unambiguous canonical-name matching. | Baseline; never replace an existing UUID. |
| `device` | Root Device containing the interface. | Baseline; the explicitly selected Device. |
| `module` | Physical Module owning the port; its root must agree with `device`. | Baseline; reviewed serialized-part and slot evidence. |
| `name` | Interface identifier. | Baseline; preserve an existing alias/name when it matches the canonical observed name. |
| `type` | Interface kind and physical capability, such as copper Ethernet, SFP, virtual, or LAG. | Baseline; reviewed hardware capability or an existing template. Negotiated speed does not determine capability. |
| `enabled` | Administrative enablement. | Baseline; structured administrative state, independent of link state. Existing `False` is populated. |
| `description` | Descriptive text. | Baseline; structured interface description, filling empty text only. |
| `mac_address` | MAC address of this interface. | Baseline; the interface's own structured MAC, excluding unavailable/sentinel values. |
| `mtu` | Interface maximum transmission unit. | Baseline; the applicable interface MTU, without substituting an unrelated protocol MTU. Model bounds are 1–65536. |
| `lag` | Assigned parent aggregation interface. | Baseline; explicit member-to-Port-channel evidence, preserving populated membership. |
| `mode` | How the interface carries 802.1Q traffic. | Supported complete configuration; directly reported ordinary dynamic access/trunk selection with known configured VLAN policy; or the explicitly enabled narrow NTC inference policy below. |
| `untagged_vlan` | The single configured untagged VLAN assignment. | This increment; access data VLAN or ordinary trunk native VLAN, with allowed-list exclusions retained as separate evidence. |
| `tagged_vlans` | Explicit VLANs carried with tags when mode is `tagged`. | This increment; finite membership after resolving VLAN objects. |
| `speed` | Operational speed in **Kbps**, stored as an integer. | This increment; known operational rate, converted from the documented source units. Unknown/down-state placeholders do not establish a rate. |
| `duplex` | Copper twisted-pair duplex setting: `auto`, `full`, or `half`. | Explicit structured configuration, or an omitted leaf within the narrowly reviewed configured-default profile below. Negotiated/MAC duplex remains observations. |
| `port_type` | Physical connector, such as `8p8c` or `lc`. | This increment; explicit `ether-media-type-rj45` maps to `8p8c` only on physical interfaces. Other connectors require reviewed evidence; an SFP capability alone does not establish an optical connector. |
| `mgmt_only` | Used exclusively for out-of-band management. | The reviewed C9300-48UXM/member-1 dedicated `Gi0/0` profile permits the narrow documented `False` to `True` purpose correction. Preserve other values; reachability, an IP, or a management-like VRF/name alone is insufficient. |
| `vrf` | Routing/forwarding domain assigned to the interface. | Management configuration is report-only; resolve Device-local VRF identity and Namespace before assigning. |
| `ip_addresses` | Many-to-many assignment of IPAddress objects, with assignment metadata. | Management static address/mask configuration is report-only; Namespace, parent prefix and address-role evidence are required before assigning. |
| `parent_interface` | Parent of a virtual subinterface. | Future; explicit structured parent relationship, independent of `lag` and `module`. |
| `bridge` | Another interface serving as its bridge. | Future; explicit bridge membership. A VLAN SVI is not automatically a bridge parent. |
| `breakout_position` | Lane position on a breakout parent connector. | Future; explicit breakout evidence. It is not the numeric suffix of an arbitrary subinterface. |
| `label` | Physical faceplate label. | Preserve; do not copy interface name or configured description into it. |
| `role` | Operator-defined functional role. | Preserve; requires an agreed taxonomy and mapping. |
| `status` | Applicable Nautobot operational/inventory status. | Baseline creation input; defaults to an applicable Active status. Preserve existing status; link-down does not establish Failed or Maintenance. |
| `tags` | Operator-defined organizational tags. | Preserve; no automatic taxonomy inference. |
| `_custom_field_data` | Values of configured custom fields. | Preserve existing values. Discovery does not create or populate custom fields. |
| `created`, `last_updated` | Nautobot-maintained timestamps. | Managed by Nautobot. |
| `_name` | Internal natural-ordering value derived from `name`. | Managed by Nautobot. |

Nautobot has no native Interface fields for PoE mode, PoE allocation/draw, Cisco voice-VLAN policy, DTP state, counters, STP state, or general link-up/link-down state in 3.2.5. Such data remains structured report observations until an appropriate native model and interpretation are established. A PSU PowerPort is not an Ethernet PoE port.

The dedicated-management correction requires exact reviewed hardware provenance and an observed physical `Gi0/0`; it never sets `mgmt_only=False`. Existing incompatible type/connector, Module ownership, LAG membership or VLAN settings defer the correction. The Device's reachable `Vlan2` address does not establish an out-of-band Interface purpose. Structured management VRF, IPv4 masks, configured IPv6 prefixes and address flags are retained in `discovery.management` while Namespace/VRF assignments remain deferred.

Physical console connectors use native `ConsolePort`, not `Interface` or `ConsoleServerPort`. For the reviewed C9300-48UXM/member-1 profile, Cisco's documented rear RJ45/front USB mini-B connectors map to `rj-45`/`usb-mini-b`. Their model-specific source and standardized-name provenance are recorded independently of NTC guessing. Existing names, UUIDs, populated labels/descriptions/types, Module ownership and cables are preserved; ambiguous matches are never duplicated. The one native console line is separate from those two physical connectors. Nautobot 3.2.5 has no ConsolePort baud, parity, stop-bit, enabled or operational-status field, so such configured settings remain report observations without custom fields. See the [Cisco connector specification](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/hardware/install/b_c9300_hig/connector-cable-specs.html) and [native console model](https://github.com/nautobot/nautobot/blob/v3.2.5/nautobot/dcim/models/device_components.py).

The installed form defines three 802.1Q modes:

| Structured forwarding meaning | Nautobot `mode` | VLAN assignments |
| --- | --- | --- |
| One untagged VLAN | `access` | `untagged_vlan`; no `tagged_vlans`. |
| A finite set of tagged VLANs, optionally with an untagged VLAN | `tagged` | `tagged_vlans`; optional `untagged_vlan`. |
| All VLANs available, optionally with an untagged VLAN | `tagged-all` | Optional `untagged_vlan`; no expanded tagged list. |
| Routed interface, or no established 802.1Q forwarding meaning | Empty | No inferred VLAN membership. |

These describe configured tagging semantics, so Cisco's spelling of a switchport mode is only part of the evidence. A port carrying untagged data and a tagged voice VLAN fits Nautobot `tagged`, even when Cisco calls it access. Voice-VLAN policy, dynamic negotiation, enabled native-VLAN tagging, private VLANs, and QinQ remain unresolved unless structured evidence and a reviewed mapping establish their meaning. An SVI is not an ordinary switchport, and its name does not establish a switchport mode. Missing configuration leaves remain unknown except within the reviewed default profile below.

Administrative mode and eventual forwarding mode are separate facts. A known `dynamic-auto` or `dynamic-desirable` configuration does not determine whether the port will carry access or trunk traffic. The job retains available settings under **Advanced → Worker → Meta → discovery_report → discovery → layer2 → settings**, and in the report download: configured administrative mode, access VID, trunk-native VID, allowed policy, and their field/source evidence. A dynamic port receives `access` only when the optional source below directly establishes that actual mode and its configured VLAN policy is known. No custom fields are created. An access VID and trunk-native VID can differ and must remain distinct. Only proven equal access/native VIDs with ordinary untagged semantics establish a common `untagged_vid` observation before an actual mode is known. Even a known common VID cannot populate Nautobot's `untagged_vlan` when `mode` remains blank, because the model forbids that combination. The explicit NTC opt-in below permits a narrow inferred `tagged-all` mapping and its known trunk-native VID instead; it does not establish a common access/native VID or a device-reported forwarding state.

Known dynamic configuration without a usable actual-mode source and reviewed defaults are informational classifications. Management interfaces, SVIs, and explicit `no switchport` routed interfaces are not applicable to ordinary switchport mapping. Failed source reads, unsupported default profiles, and unreviewed switching meanings retain genuine unresolved classifications and warnings. A disconnected port is still eligible: supported configuration does not depend on link state.

## Optional actual switchport mode

The advertised native `Cisco-IOS-XE-switchport-oper` module provides actual status after negotiation at `/data/Cisco-IOS-XE-switchport-oper:switchport-oper-data`, keyed by `switchport-info/if-name`, in `port-details/oper-mode`. The [published IOS XE 17.14.1 model](https://github.com/YangModels/yang/blob/main/vendor/cisco/xe/17141/Cisco-IOS-XE-switchport-oper.yang) has revision `2024-03-01`. `oper-stat-acc` and `oper-dyn-acc` establish access; `oper-trunk` establishes trunk; `oper-down` does not establish either. Canonical interface-name matching must be unique. Rows must report switchport operation, present hardware, and an ordinary administrative mode before their actual mode is usable. Here the YANG empty leaf `enabled` means switchport versus routed operation; it is unrelated to Nautobot's administrative `Interface.enabled`.

For ordinary dynamic configuration, a compatible directly reported access/trunk result selects the already known configured access VID or trunk native/allowed policy. The existing mapping then produces `access`, `tagged`, or `tagged-all` and the corresponding VLAN relationships without the NTC guessing flag. Explicit configured access/trunk mode retains precedence. A reported dynamic administrative enum can establish an omitted mode on an otherwise complete native configuration row, but does not establish missing VLAN settings or broaden the existing default profile. Native tagging and VLAN Group/catalog validation still apply. Voice/private-VLAN/tunnel semantics, routed operation, suspended aggregation, or disagreement with configured LAG membership block the affected bundle; an actual access/trunk result conflicting with the independently reported down link also remains unresolved.

`discovery.layer2.operational_source` records capability status and source module/path/revision. `discovery.layer2.operational_interfaces` preserves every reported interface and its raw observations, including those without a native configuration row. Where configuration is available, `discovery.layer2.settings` also records operational mode, raw `switchport_oper` observations, and field/source evidence. Operational access/native VLAN IDs, current trunk ranges, pruning ranges, voice state, and aggregation context remain observations, rather than configured VLAN assignments. This adds no custom field or native Interface column. Down, unknown, or unsupported actual mode preserves unresolved assignments as blank. The existing NTC down-port policy may operate on an ordinary reported down mode only when its independent link-down proof and every existing guard hold; positive, unknown, conflicting, or special reported modes cannot be replaced by that assumption.

No endpoint request is made when the module is `not-advertised` or its availability is `capability-unknown` because the YANG library could not be read. An advertised source that fails to read is `unavailable`, preserving discovery from other sources; malformed or ambiguous advertised data blocks discovery. Successful reads are `available`. Capability detection allows older IOS XE versions to retain their existing behavior without a software-version assumption. Summary `switching_operational` counts positive access/trunk observations across all reported interfaces; `switching_dynamic_resolved` counts complete actual-mode-based dynamic bundles, rather than newly written assignments.

The IOS XE 17.12.8 lab does not advertise this module; a separate GET probe returned HTTP 404. Three correctly keyed VTP-MIB RESTCONF probes timed out after 30 seconds each, so that alternative is not part of this implementation. OpenConfig's VLAN state grouping mirrors applied configuration, rather than establishing DTP-negotiated mode; see its [applied-versus-derived state extension](https://github.com/YangModels/yang/blob/main/vendor/cisco/xe/17121/openconfig-extensions.yang#L159). No device configuration or MIB access was changed. Positive newer-release cases are validated against published-schema offline fixtures, not a live newer-release switch.

## Optional NTC inference

The **Use NTC defaults when guessing** Job input (`use_ntc_defaults`) defaults to **False**. Enabling it opts into policy `ntc-device-onboarding-5.4.1-dynamic-down-all`, reviewed from [Network to Code Device Onboarding 5.4.1 at commit `812746dc`](https://github.com/nautobot/nautobot-app-device-onboarding/blob/812746dc6f09077b8fe099da2318315e4e7cab23/nautobot_device_onboarding/jinja_filters.py#L86). Its `_interface_mode_logic` maps a dynamic administrative mode with operational mode `down` and allowed `ALL`/`1-4094` to `tagged-all`; `get_vlan_data` uses the native VLAN as untagged for that mode. This project adopts only that narrow normalization fallback. It is an inference policy, not a Cisco default or proof of the port's eventual negotiated mode.

Eligibility requires supported physical switching, known dynamic configuration, a complete allowed-all policy, known trunk-native VID, and ordinary untagged native semantics with native tagging disabled. The RESTCONF operational leaf must be exactly `if-oper-state-no-pass` or `if-oper-state-lower-layer-down`; up, testing, dormant, absent, and other values do not qualify. These are the accepted structured down states for this adaptation, rather than a CLI parsing fallback. Unavailable/incomplete source reads, malformed data, finite restrictions, voice/private/tunnel configurations, unsupported types, and unknown/enabled native tagging cannot be bypassed by the flag. Native VLAN object resolution and Nautobot validation still require the selected group and applicable VLAN identity. The job never adopts the upstream placeholder-name fallback.

Allowed-policy eligibility accepts explicit `ALL` and the validated exact configured literal `1-4094`. Composed range expressions covering the same set and other finite ranges are excluded to retain parity with the upstream rule. The configured fact remains a list when the source is `1-4094`; only the separately identified inference proposes `tagged-all`. No normalization rewrites that source configuration as an explicit all-VLAN setting.

The top-level report records the selected `use_ntc_defaults` value. Each eligible setting records `inference`; each inferred complete bundle records `source.ntc_inference`. Provenance identifies the policy and upstream source, actual RESTCONF state with module/path, administrative mode, inferred `tagged-all` and native VID, and explicit assumption meaning. The `switching_inferred` summary counts matching observations; `interface_vlan_assignments_inferred` counts actual planned inferred writes, which can be zero on a repeat. Main logs identify the opt-in and inference counts. Guessed fields therefore remain distinguishable from explicit configuration and documented Cisco defaults in the saved report.

With the flag disabled, values lacking a complete configuration mapping or usable direct actual-mode evidence remain unresolved. Disabling it later preserves previously populated inferred mode/VLAN assignments under the existing fill-only contract; it does not clear operator inventory or erase the original report. No inference is enabled for other interface/device fields by this initial policy.

## VLAN configuration and identity

For an ordinary finite trunk, the configured native VLAN is represented by `untagged_vlan`, and the explicit tagged set excludes that untagged VLAN. Preserve the native assignment even when the configured allowed list excludes that VID: Nautobot records the configured native role, rather than claiming that user traffic currently forwards in that VLAN. Keep the raw allowed-list exclusion in the report as separate evidence. Do not turn a configured unrestricted trunk into the list of VLANs active today: `tagged-all` also expresses availability beyond the current catalog. Conversely, an incomplete read of an allowed list does not establish unrestricted forwarding.

The reviewed default profile is limited to **C9300-48UXM running IOS XE 17.9.x, 17.12.x, or 17.15.x**, with successful, scoped, complete structured reads of the relevant interface and global VLAN configuration. Cisco's [17.9 VLAN command reference](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-9/command_reference/b_179_9300_cr/vlan_commands.html) and [17.12 VLAN command reference](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-12/command_reference/b_1712_9300_cr/vlan_commands.html) document native VID 1 and an unrestricted allowed list as the `switchport trunk` defaults, and disabled global native tagging as the `vlan dot1q tag native` default. On an explicitly configured trunk in this profile, omitted native/allowed leaves in a complete read can therefore establish native VID 1 / allowed-all. A successful complete read of the global `native/vlan` scope, including a successful HTTP 204 empty response, establishes disabled native tagging when the configured empty enable leaf is absent. A present enable leaf means enabled native tagging and follows the unresolved handling above.

The corresponding [17.12 interface defaults](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-12/configuration_guide/int_hw/b_1712_int_and_hw_9300_cg/configuring_interface_characteristics.html) and [17.9 interface defaults](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-9/configuration_guide/int_hw/b_179_int_and_hw_9300_cg/configuring_interface_characteristics.html) establish dynamic-auto administrative mode and access VLAN 1 for reviewed ordinary switchports. An omitted access VID on an explicitly configured ordinary access port can therefore fill native `mode = access` and untagged VLAN 1 after a complete supported read. An omitted administrative mode is retained as documented dynamic-auto configuration; actual forwarding mode remains unresolved unless directly reported as described above. [Cisco's trunk negotiation guidance](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-12/configuration_guide/vlan/b_1712_vlan_9300_cg/configuring_vlan_trunks.html) establishes why a dynamic mode alone cannot prove a single access/trunk result.

The same Layer 2 profile is reviewed for 17.15.x: Cisco's [17.15 interface defaults](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-15/configuration_guide/int_hw/b_1715_int_and_hw_9300_cg/configuring_interface_characteristics.html) establish dynamic auto, access/native VID 1, and the unrestricted allowed range; the [17.15 VLAN reference](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-15/command_reference/b_1715_9300_cr/vlan_commands.html) establishes disabled native tagging. The [17.15 management guide](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-15/configuration_guide/int_hw/b_1715_int_and_hw_9300_cg/configuring_ethernet_management_port.html) identifies Gi0/0 as the dedicated management interface. This extension allows a device-reported 17.15 dynamic access/trunk result to select those documented VLAN settings after complete scoped reads. It does not widen the separate configured-duplex profile or hardware capability mappings. Other releases, including 17.16/17.18, receive no omitted-leaf defaults from this profile.

Every use of this profile must annotate the observation with the reviewed model/release, request scope and completion evidence, omitted leaf, documented default, and supporting command-reference URL. It is a documented interpretation of a successful configuration read, not a general missing-field heuristic. Failed requests, incomplete/unsupported response shapes, unknown read completeness, unreviewed releases, and other device families retain unresolved values; they do not inherit these defaults. No CLI query is required or permitted for this interpretation.

VLAN identity is **selected VLAN Group UUID + VID**, never VID alone or a guessed VLAN name. The lab explicitly selects the group named `lab`; its scope is global and its configured VID range is 1–4094. A VLAN Group is a discovery scope, not an Interface field. [Nautobot's VLAN Group documentation](https://archive.docs.nautobot.com/projects/core/en/v3.2.2/user-guide/core-data-model/ipam/vlangroup/) describes uniqueness of IDs and names within a group. [Its VLAN modeling guidance](https://archive.docs.nautobot.com/projects/core/en/v3.2.2/user-guide/core-data-model/ipam/vlan/) requires separate records for separate Layer 2 domains sharing an ID, and a shared record only where Layer 2 is actually stretched.

A complete structured VLAN database can establish **all observed named VLANs** inside the explicitly selected group, including VLANs without interface membership. The adapter marks that catalog complete only after a successful supported database read. Older discovery schemas without the marker retain referenced-only reconciliation. Names must come from that database. Creation status is an operator input with an applicable Active default, independent of device link or VLAN operational state. Preserve existing names/status and report disagreements. Duplicate names, unavailable names, missing scope, unsupported ranges, or ambiguous identities leave the affected catalog entry or relationship unresolved. Without a selected group, the job performs no VLAN writes. Never create placeholder names such as `VLAN100`, infer tenancy/role, or populate thousands of VLANs for `tagged-all`.

An untagged assignment requires nonempty `mode`. A tagged assignment requires `mode == tagged`. For either assignment, a VLAN must be global or associated with the Device's location or an ancestor location. A VLAN Group's location does not substitute for the VLAN's own location associations. These rules are implemented in the [Interface model](https://github.com/nautobot/nautobot/blob/v3.2.5/nautobot/dcim/models/device_components.py), [tagged membership validator](https://github.com/nautobot/nautobot/blob/v3.2.5/nautobot/dcim/utils.py), and [API serializer](https://github.com/nautobot/nautobot/blob/v3.2.5/nautobot/dcim/api/serializers.py).

Saving an existing interface with a mode other than `tagged` automatically clears its tagged-VLAN relationship in Nautobot. The job must detect this before saving: never fill an incompatible mode over a populated tagged set, and never discard existing membership as a side effect of enriching another field. Existing populated mode, untagged assignment, and tagged sets are preserved on disagreement. Dry-run must validate proposed foreign keys and tagged membership without calling `.set()`, `.add()`, `.clear()`, or saving temporary parents. Apply saves required VLAN and Interface objects before relationship writes, within the same atomic transaction.

Speed and duplex are separate from capability and administrative state. Model validation forbids either on LAG, virtual, or wireless interface types, and permits duplex only on copper twisted-pair types (`100base-tx`, `1000base-t`, `2.5gbase-t`, `5gbase-t`, `10gbase-t`). Optical/backplane types can have operational speed but must leave duplex empty even if the device reports full duplex. The speed unit and supported duplex values are documented in the [3.2.5 Interface guide](https://raw.githubusercontent.com/nautobot/nautobot/v3.2.5/nautobot/docs/user-guide/core-data-model/dcim/interface.md). Configured bandwidth, maximum hardware rate, and a negotiated-rate placeholder on a down link are not operational speed. Filling a blank captures an observation; later rate changes are reported as conflicts under this job's fill-only policy.

The duplex write contract is **configured values only**. The [originating feature issue #6979](https://github.com/nautobot/nautobot/issues/6979) describes configuration generation; the guide calls duplex a setting and includes `auto`, while [merged PR #8053](https://github.com/nautobot/nautobot/pull/8053) groups speed and duplex under a shared operational-attributes comment. Those sources do not explicitly establish that negotiated `full` should represent configured `auto`. Model/API acceptance proves that a value is valid, not that this interpretation is intended. The collector reads qualified `Cisco-IOS-XE-ethernet:duplex` from a complete native interface scope and accepts explicit `auto`, `full`, or `half` only on supported copper types. Operational `ether-state` negotiated duplex and RFC 3635 MAC current-duplex remain observations, even when they agree.

The configured-default profile is deliberately narrower than the switchport profile: **C9300-48UXM, IOS XE 17.9.x/17.12.x, member 1**, fixed `TwoGigabitEthernet1/0/1`–`1/0/36` with type `2.5gbase-t`, plus management `GigabitEthernet0/0` with type `1000base-t`. A present row in a complete native read with an omitted duplex leaf establishes documented configured `auto` for those reviewed interfaces. [Cisco's 17.12 interface command reference](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-12/command_reference/b_1712_9300_cr/interface_and_hardware_commands.html) and the interface-default guides above support the configured interpretation; every default includes its profile and document evidence. TenGigabitEthernet, optical, other-member, unknown-type, and unreviewed ports do not inherit this default. Missing native rows, failed/incomplete reads, a ready link, or `auto-negotiate = false` in operational data do not establish a configured setting. Existing populated duplex remains preserved on disagreement.

Connector discovery maps the explicit structured value `ether-state.media-type == ether-media-type-rj45` to `port_type = 8p8c` only when the Interface type is physical; virtual, wireless, and LAG types remain excluded by Nautobot validation. Cisco's [IOS XE interfaces operational YANG model](https://github.com/YangModels/yang/blob/main/vendor/cisco/xe/17121/Cisco-IOS-XE-interfaces-oper.yang#L4144) defines this leaf as the type of media attached to the interface and [enumerates RJ45](https://github.com/YangModels/yang/blob/main/vendor/cisco/xe/17121/Cisco-IOS-XE-interfaces-oper.yang#L1196). The [C9300 connector specification](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/hardware/install/b_c9300_hig/connector-cable-specs.html) documents standard RJ45 Ethernet connectors, and Cisco explicitly identifies Ethernet RJ45 as [8P8C in its hardware terminology](https://www.cisco.com/c/en/us/td/docs/security/firepower/1100/hw/guide/hw-install-11001/overview.html). Nautobot's [3.2.5 connector choice](https://github.com/nautobot/nautobot/blob/v3.2.5/nautobot/dcim/choices.py#L1230) is `8p8c`. This connector remains observable when the link is down: the lab reports the explicit enum on all 48 front-panel copper ports and the management port. Preserve an existing different connector as a conflict. Missing values, `ether-media-type-none`, auto-selection, generic copper capability, and operational speed do not establish a connector; SFP/SFP+ capability or media alone does not establish LC or another optical connector.

Future routing discovery must resolve the Device's VRF assignments, including their local name/RD overrides. VRF names are not globally unique; RD uniqueness is scoped to a Namespace, and names can still be duplicated. Assign the VRF to the Device before assigning it to an Interface. IP addresses inherit namespace and VRF associations from their parent prefixes; address uniqueness is namespace/host based, and `mask_length` records the configured mask rather than selecting the parent prefix. Resolve the intended Namespace, existing parent Prefix, existing IP object and mask compatibility before assigning an address. Do not infer the global Namespace merely because an interface is in the device's default routing table. See the [VRF model](https://github.com/nautobot/nautobot/blob/v3.2.5/nautobot/ipam/models.py), [VRF guide](https://archive.docs.nautobot.com/projects/core/en/v3.2.2/user-guide/core-data-model/ipam/vrf/), and [IP Address guide](https://archive.docs.nautobot.com/projects/core/en/v3.2.2/user-guide/core-data-model/ipam/ipaddress/).

The [IPAM migration guide](https://docs.nautobot.com/projects/core/en/stable/user-guide/administration/upgrading/from-v1/ipam/whats-changed/) additionally describes restricting an interface's IPs to children of its VRF's assigned prefixes when those prefixes exist. The installed 3.2.5 `IPAddressToInterface.full_clean()` validates endpoint choice and uniqueness, rather than implementing that entire documented restriction. Future discovery should explicitly enforce the intended routing/namespace consistency instead of assuming ORM acceptance proves correct semantics. IP assignments are many-to-many and support source/destination/default/preferred/primary/secondary/standby flags; none is interchangeable with selecting the Device's primary management IP.

For future subinterface discovery, a parent must be distinct and on the same Device or virtual chassis; only type `virtual` can have `parent_interface`. Breakout positions are 1–256, require a parent, and are unique within that parent. The bridge target must also be distinct and on the same Device or virtual chassis. The job can retain its stricter selected-Device boundary. Neither relationship is interchangeable with an SVI's VID, Module ownership, or LAG membership. See the [3.2.5 model validation](https://github.com/nautobot/nautobot/blob/v3.2.5/nautobot/dcim/models/device_components.py).

The [3.2.5 Interface table](https://github.com/nautobot/nautobot/blob/v3.2.5/nautobot/dcim/tables/devices.py) offers these configurable fields: `pk`, `device`, `module`, `name`, `status`, `role`, `label`, `enabled`, `type`, `port_type`, `speed`, `duplex`, `breakout_position`, `mgmt_only`, `mtu`, `vrf`, `mode`, `mac_address`, `description`, `cable`, `cable_peer`, `connection`, `tags`, `ip_addresses`, `untagged_vlan`, `virtual_device_context_count`, `tagged_vlans`, and `actions`. The `pk`/`actions` columns serve table selection and UI actions. Cable, cable peer, and connection columns derive from modeled cable terminations/paths; the virtual-device-context column is a relationship count. LLDP/CDP adjacency alone does not establish a physical cable or path, so these remain operator-maintained. Parent interface, LAG, and bridge are native fields exposed elsewhere, even though they are not in this table's configurable field list.

Compatibility must be checked per field and relationship. Speed/duplex were added in 2.4.22, connector `port_type` in 3.1.0, and breakout positions in 3.2.0. VLAN locations became many-to-many in 2.2; Namespace and IP-assignment semantics changed in 2.0. Module root-device denormalization also differs across releases. The 3.2.5 mapping must not silently claim support for an older schema: detect absent fields, retain the observations, and report unsupported writes. The first verification target remains 3.2.5.
